# Sécurité — principes, modèle de menace et schéma cryptographique

> Document de référence pour toute implémentation qui touche aux secrets, au réseau, à l'IPC, aux fichiers ou à la CI.
> Il n'est modifié qu'avec l'accord du porteur. Claude Code demande avant de l'éditer.

## 1. Ce qu'on protège
| Actif | Pourquoi c'est sensible |
|---|---|
| Mots de passe, clés privées, passphrases, codes OTP | Accès direct aux serveurs |
| Liste des hôtes, utilisateurs, groupes, notes | Cartographie de l'infrastructure, utile à un attaquant |
| Sessions ouvertes | Accès en cours, pivot réseau |
| Intégrité des connexions | Une attaque de l'homme du milieu permet de voler des identifiants et de lire ou modifier la session |
| Intégrité de l'application et des mises à jour | Une application piégée a accès à tout |

## 2. Menaces prises en compte
| # | Menace | Parade principale |
|---|---|---|
| M1 | Vol du fichier de coffre (PC volé, sauvegarde qui fuite, malware qui exfiltre le fichier) puis attaque par force brute hors ligne | Chiffrement fort, Argon2id coûteux, mot de passe maître robuste exigé (§3) |
| M2 | Homme du milieu sur le réseau | Vérification des clés d'hôte (TOFU strict), certificats RDP (§4) |
| M3 | Serveur malveillant ou compromis | Validation des noms de fichiers SFTP, filtrage des séquences d'échappement dangereuses, questions keyboard-interactive nettoyées, bornées et signalées comme venant du serveur (anti-hameçonnage), pas d'agent forwarding (§4, §6) |
| M4 | Dépendance npm compromise exécutée dans la WebView | Secrets absents de la WebView, CSP, capabilities minimales, `cargo-deny` / `npm audit` (§5, §8) |
| M5 | Fuite par effet de bord : journaux, liste des processus, messages d'erreur, fichiers temporaires, presse-papiers | Règles du §6 |
| M6 | Mise à jour piégée | Mises à jour signées, clé privée hors du dépôt (§7) |
| M7 | Erreur de manipulation : diffusion vers les mauvais serveurs | Valeurs par défaut sûres, avertissements visibles (§6) |

**Hors du modèle** : un malware qui tourne sur la machine avec les droits de l'utilisateur **pendant que le coffre est déverrouillé** (keylogger, lecture de la mémoire). On réduit l'exposition (verrouillage automatique, effacement de la mémoire), mais on ne peut pas s'en protéger complètement. Il faut le dire honnêtement dans la documentation publique.

## 3. Coffre chiffré (étape 2)

### 3.1 Hiérarchie de clés
```
mot de passe maître ──Argon2id(sel)──► KEK (32 octets, jamais stockée)
                                         │
                                         ▼ XChaCha20-Poly1305 (wrap)
DEK (32 octets aléatoires, OsRng) ──────► DEK chiffrée, stockée dans l'en-tête
                                         │
                                         ▼ XChaCha20-Poly1305
données du coffre (sérialisées) ────────► charge utile chiffrée
```
- **Changer le mot de passe maître** : nouveau sel, nouvelle KEK, **nouvelle DEK**, et tout le fichier est rechiffré avec de nouveaux nonces. Deux raisons : l'en-tête (sel compris) sert d'AAD à la charge utile, donc on ne peut pas changer le sel sans la rechiffrer ; et sans rotation de la DEK, une ancienne copie du coffre ouverte avec l'ancien mot de passe donnerait la clé des versions futures. Le déverrouillage par le système (étape 10) doit alors être réactivé.
- **Le déverrouillage par le système** (étape 10) stocke la DEK protégée par le système d'exploitation. Le mot de passe maître reste toujours valable.

### 3.2 Primitives et paramètres
| Élément | Choix |
|---|---|
| Dérivation | **Argon2id**, m = 64 Mio, t = 3, p = 4 (paramètres stockés dans l'en-tête pour pouvoir les augmenter). Refuser d'ouvrir un fichier dont les paramètres sont sous ce plancher **ou au-dessus d'un plafond** (m ≤ 1 Gio, t ≤ 10, p ≤ 16) : un coffre ou une sauvegarde piégés ne doivent pas pouvoir saturer la mémoire. |
| Sel | 16 octets aléatoires, nouveau à chaque changement de mot de passe |
| Chiffrement | **XChaCha20-Poly1305** (crate `chacha20poly1305`), nonce aléatoire de 24 octets, **nouveau à chaque écriture** |
| Données associées (AAD) | L'en-tête complet (magie, version, paramètres KDF, sel) est authentifié, ce qui empêche de modifier les paramètres ou la version sans être détecté |
| Aléa | `rand::rngs::OsRng` uniquement |
| Sérialisation | JSON via `serde`, avec un champ `schema_version` (simple à faire évoluer et à déboguer, la taille n'est pas un enjeu) |

### 3.3 Format de fichier v1 (`vault.younji`)
```
"YNJV" (4) | version u16 = 1 | kdf_id u8 = 1 (Argon2id) | m_kib u32 | t u32 | p u32 | sel (16)
| nonce_dek (24) | DEK chiffrée + tag (48)
| nonce_data (24) | longueur u64 | données chiffrées + tag (16)
```
Entiers en little-endian. La longueur annoncée est vérifiée **avant toute allocation** : elle doit correspondre à la taille réelle du fichier et rester sous 64 Mio. Toute erreur de déchiffrement donne le même message (`vault.wrong_password_or_corrupted`), sans distinguer les deux cas.

### 3.4 Mot de passe maître
- Minimum 12 caractères, et estimation de robustesse avec `zxcvbn` (score ≥ 3 exigé, avec une explication si le mot de passe est refusé).
  - **Mise en œuvre (étape 2, ADR-029)** : le contrôle **fait foi dans le cœur** (crate `zxcvbn`, `core-vault/src/policy.rs`), à la création comme au changement de mot de passe. L'interface affiche un indicateur en direct calculé localement par `@zxcvbn-ts` (dictionnaires chargés à la demande), pour ne pas envoyer le mot de passe au cœur à chaque frappe ; en cas de divergence, le refus du cœur s'affiche.
- Aucune récupération possible si on l'oublie. Il faut le dire clairement à la création, et proposer l'export chiffré (étape 9) comme sauvegarde.
- Délai progressif après plusieurs échecs dans l'interface. C'est surtout du confort : la vraie protection contre M1 reste Argon2id.
  - **Mise en œuvre (étape 2)** : imposé **par le cœur** (`src-tauri/src/vault_state.rs`), pas par l'interface. Les tentatives sont traitées une à une ; après 3 échecs consécutifs, chaque tentative attend 1 s, 2 s, 4 s… jusqu'à 30 s. La vérification du mot de passe actuel lors d'un changement partage ce compteur, pour qu'elle ne serve pas d'oracle sans ralentissement.

### 3.5 Cycle de vie en mémoire
- DEK et secrets déchiffrés dans `SecretBox` / `SecretString`, effacés (`zeroize`) au verrouillage et à la fermeture.
- Argon2 tourne dans `spawn_blocking` pour ne pas figer l'application.
- **Verrouillage** : la DEK et tous les secrets déchiffrés sont supprimés. Le comportement des sessions déjà ouvertes est à décider à l'étape 2 (ADR).
  - **Décision (étape 2, ADR-026)** : tout verrouillage (manuel, Ctrl+Maj+L ; inactivité ; rechargement de l'interface) **ferme toutes les sessions SSH** et l'interface **détruit les onglets et les terminaux**, tampon de défilement compris. Le coffre est verrouillé avant la fermeture des sessions, et une session enregistrée pendant le verrouillage est refermée aussitôt.
  - **Verrouillage automatique** : le minuteur tourne **dans le cœur**. L'interface ne fait que signaler l'activité au clavier, à la souris ou à la molette (au plus toutes les 15 s) ; elle ne décide pas du verrouillage. Deux horloges sont comparées au délai (monotone et murale) : la mise en veille compte, et une horloge murale qui recule n'empêche jamais le verrouillage. Délai de 1 à 60 min (15 par défaut), **sans option « jamais »**, stocké dans le coffre (authentifié) et non dans `settings.json`.
  - **Toute l'application est derrière le déverrouillage** (ADR-028) : carnet, terminaux et connexion rapide ne s'affichent qu'une fois le coffre ouvert.
- Limite connue : Rust ne garantit pas l'absence de copies (swap, réallocations). On limite les copies, sans promettre l'impossible.

### 3.6 Écriture
- Écriture atomique : fichier temporaire dans le même dossier, `fsync`, puis renommage par-dessus l'original (`tempfile::NamedTempFile::persist`). La version précédente devient `vault.younji.bak`.
- Permissions : 0600 pour les fichiers et 0700 pour le dossier sous Linux. Sous Windows, le profil utilisateur (`%APPDATA%`) suffit.
- **Mise en œuvre (étape 2)** :
  - La copie `.bak` est elle aussi écrite de façon atomique, avant le remplacement du fichier principal. Un dossier de données déjà existant avec d'autres droits est ramené à 0700 sous Linux.
  - Après un **changement de mot de passe**, le `.bak` est recopié depuis le nouveau fichier : l'ancien mot de passe n'ouvre plus aucune copie gérée par Younji.
  - La création n'écrase jamais un fichier (`persist_noclobber`) et elle est **refusée si seul le `.bak` existe** (`vault.backup_only`) : sinon la première sauvegarde écraserait la seule copie restante. L'utilisateur la restaure en la renommant.
  - **Limite connue** : l'écrasement d'un fichier ne garantit pas l'effacement physique des anciennes versions (SSD, journal du système de fichiers, sauvegardes du système, clichés instantanés). Une ancienne copie du coffre récupérée par ces moyens reste protégée par l'**ancien** mot de passe : après une fuite présumée de celui-ci, la protection des données déjà sauvegardées ailleurs ne peut pas être garantie.
- **`settings.json`** (langue, thème, taille de police) est en clair, car il doit être lisible avant le déverrouillage. Il ne contient **aucune donnée sensible** ; chaque valeur relue est validée et une valeur inattendue reprend sa valeur par défaut.

### 3.7 Export chiffré (étape 9)
Même schéma, avec la magie `"YNJB"`, un **sel distinct** et une **phrase de passe distincte** du mot de passe maître. Un fichier altéré est rejeté (tag AEAD).

## 4. Connexions

### 4.1 SSH
- **Clés d'hôte** : confiance à la première connexion. On affiche l'algorithme et l'empreinte `SHA256:…`, au format OpenSSH, pour pouvoir la comparer avec `ssh-keygen -lf`. Règle stricte (ADR-023) : si l'hôte est déjà connu et que la clé présentée n'est pas dans la liste enregistrée, **même si elle est d'un autre type**, la connexion est **refusée**, sans bouton « continuer quand même » et avant tout envoi d'identifiant. Cette règle empêche un homme du milieu de proposer un autre algorithme pour retomber sur une simple demande de confiance. Une ligne illisible qui nomme l'hôte compte comme une clé connue : elle bloque au lieu de redemander confiance. Une clé `@revoked` est refusée. La clé acceptée n'est enregistrée qu'après la vérification, par russh, de la signature du serveur sur l'échange de clés : le serveur a prouvé qu'il détient la clé privée. Pour débloquer, il faut supprimer explicitement l'ancienne clé : à la main dans `known_hosts` jusqu'à l'étape 2 (l'alerte indique le fichier et la ligne), puis dans la gestion des clés d'hôte (HKY-04), après un avertissement.
  - **Depuis l'étape 2 (ADR-027)** : les clés d'hôte connues sont stockées **dans le coffre** (format OpenSSH conservé), donc chiffrées et **authentifiées** : un logiciel tiers ne peut plus ni lire la liste des serveurs ni y glisser la clé d'un attaquant en modifiant un fichier en clair. L'ancien fichier `known_hosts` est repris à la création du coffre puis supprimé. Le déblocage se fait dans Clés > Clés d'hôte connues : la suppression désigne la ligne exacte et demande une confirmation qui rappelle de vérifier l'empreinte auprès de l'administrateur.
- **Algorithmes** : liste explicite dans `crates/core-ssh/src/config.rs`, sans dépendre des défauts de russh (ADR-019) : échange de clés hybride post-quantique `mlkem768x25519-sha256` en tête, puis curve25519, ECDH NIST et DH groupes 14/16/18 en SHA-2, avec « strict kex » (parade à Terrapin) ; ChaCha20-Poly1305 et AES-GCM, AES-CTR en repli avec MAC *-etm SHA-2 ; signatures RSA uniquement en SHA-2. SHA-1, CBC, 3DES, DSA, DH group exchange, la compression et `none` sont **désactivés** ; un test échoue s'ils réapparaissent. Une option par hôte « algorithmes hérités » (pour les vieux équipements réseau) pourra être ajoutée via un ADR, avec un avertissement visible.
- **Authentification en plusieurs méthodes et 2FA (étape 3, AUTH-03)** : la méthode `none` révèle d'abord les méthodes acceptées, puis la clé, le mot de passe et keyboard-interactive sont essayés **dans cet ordre et selon ce que le serveur propose**, succès partiels compris (`AuthenticationMethods publickey,keyboard-interactive`). Chaque moyen n'est utilisé qu'une fois.
  - Les questions du serveur sont des données non fiables : caractères de contrôle, invisibles et de mise en forme retirés (catégorie Cc, et liste explicite des principaux caractères Cf, Zl et Zp : bidirectionnel, espaces de largeur nulle, séparateurs de ligne, étiquettes), nom ≤ 256 octets, instructions ≤ 2 Kio, question ≤ 512 octets, **8 questions par demande et 16 demandes au plus** (au-delà : `ssh.auth_prompt_invalid`, sans rien montrer à l'utilisateur). L'interface les affiche en texte brut, dans un encadré « Message envoyé par le serveur », avec l'adresse de l'hôte et un rappel : Younji ne demande jamais le mot de passe maître à cet endroit (hameçonnage par un serveur malveillant).
  - **Remplissage automatique du mot de passe enregistré** : une seule fois par connexion, uniquement pour une demande d'**une seule** question **sans écho** dont le texte est exactement « Password » ou « Mot de passe » (casse, espaces et « : » ignorés), et seulement si la méthode `password` ne l'a pas déjà refusé. Toute autre question (« New password », code de vérification…) est posée à l'utilisateur. Le destinataire est le même serveur, déjà authentifié par sa clé d'hôte, que pour la méthode `password`.
  - Réponses : reçues une fois (`ssh_auth_answer`) dans des `SecretString`, nombre et longueur (octets) vérifiés par le cœur, acceptées seulement pour la demande en attente **portant le même numéro de tour** (une réponse en retard ou envoyée deux fois ne peut pas servir à la question suivante) ; jamais journalisées ni renvoyées. Délai de réponse de 2 minutes par demande, distinct des délais réseau : 30 s par échange et **60 s cumulées** pour toute l'authentification, hors temps de saisie. Fermer l'onglet, annuler ou verrouiller le coffre interrompt l'authentification.
- **Pas d'agent forwarding ni de X11 forwarding** (hors périmètre).
- **Canaux ouverts par le serveur refusés** : Younji ne demande aucun canal à l'initiative du serveur. Tout canal que le serveur tente d'ouvrir vers le poste (`session`, `direct-tcpip`, `forwarded-tcpip`, `x11`, transfert d'agent, sockets Unix) est rejeté (`administratively prohibited`), pour toutes les connexions. Par défaut, russh les accepte et ne ferme jamais ceux qu'on abandonne : un serveur malveillant pourrait en ouvrir sans limite (épuisement de mémoire). Le refus n'est journalisé qu'une fois par connexion. Un test d'intégration le vérifie.
- Les délais d'attente et le keepalive évitent les sessions zombies.

### 4.2 Contenu renvoyé par le serveur
- **Terminal** : la lecture et l'écriture du presse-papiers par séquence OSC 52 sont sans effet (aucun addon presse-papiers chargé). Les liens détectés et les liens OSC 8 ne s'ouvrent qu'en `https:`/`http:`, avec un hôte et sans identifiants intégrés, et seulement au **Ctrl+clic**. Un lien OSC 8, dont le texte affiché peut différer de la cible, passe par une confirmation qui montre l'adresse réelle. Le cœur revalide l'adresse avant de l'ouvrir dans le navigateur du système, en argument de processus et jamais via un shell (ADR-022).
- **Collage** : le mode « bracketed paste » est respecté, et un collage de plusieurs lignes ou contenant des caractères de contrôle demande une confirmation avec un aperçu où chaque caractère de contrôle est rendu visible (protection contre le « pastejacking »). Les marqueurs de début et de fin de collage (`ESC[200~`, `ESC[201~`) sont retirés **de façon répétée, jusqu'à disparition** : un marqueur imbriqué en reformerait un autre et permettrait de sortir du mode collage.
- **Déploiement de clé (KEY-03)** : la clé publique est écrite par SFTP ou transmise par l'entrée standard d'une commande fixe. Elle n'est jamais insérée dans une ligne de commande construite par concaténation.
  - **Mise en œuvre (étape 3)** : commande **constante** `sh -c '<script>'` (`crates/core-ssh/src/deploy.rs`), sans apostrophe, « ! » ni retour à la ligne, pour être lue de la même façon par tout shell de connexion ; la ligne `algorithme base64` (sans options ni commentaire) passe par l'entrée standard. Elle est **re-dérivée de la clé privée du coffre** puis revalidée (algorithme admis, base64 strict, clé décodable) : l'interface ne fournit qu'un identifiant. Le script fait `umask 077`, `chmod 700 ~/.ssh`, `chmod 600 authorized_keys` et ajoute un retour à la ligne si le fichier n'en a pas. La clé n'est « déjà présente » que si une ligne commence exactement par `algorithme base64` : une ligne commentée ou portant des options restrictives (`from=`, `command=`) ne compte pas, et la clé est alors ajoutée seule sur sa ligne. Seuls un code de retour nul **et** un marqueur exact (`YOUNJI_ADDED` / `YOUNJI_PRESENT`) valent succès ; la sortie est lue sur 1 Kio au plus. Chaque étape du canal est bornée (30 s) et le déploiement entier aussi (60 s une fois authentifié). Le déploiement suit le même chemin qu'une session (TOFU strict, 2FA) et se ferme au verrouillage. Serveurs Unix uniquement ; le comportement face à un serveur Windows (shell `cmd` ou PowerShell) est à vérifier sur le lab.
- **SFTP** : les noms de fichiers distants sont nettoyés avant toute écriture locale : refus de `..`, des séparateurs, des chemins absolus, des caractères de contrôle et des noms réservés de Windows (`CON`, `NUL`…). Le chemin final est canonicalisé et doit rester dans le dossier de destination choisi. Les liens symboliques distants ne sont pas suivis lors d'un téléchargement récursif.
  - **Mise en œuvre (étape 4, ADR-034)** :
    - **Noms refusés** pour une écriture locale (`check_local_name`, `crates/core-ssh/src/sftp/names.rs`), même règle sous Windows et Linux : vide, `.`, `..`, plus de 255 octets ; `/`, `\` et `:` (lecteur, flux NTFS `fichier:flux`) ; caractères de contrôle, invisibles ou bidirectionnels (`facture\u{202E}fdp.exe`) ; `< > " | ? *` ; point ou espace final (Windows les retire, ce qui ferait viser un autre fichier) ; noms réservés de Windows, avec ou sans extension et sans tenir compte de la casse : `CON`, `PRN`, `AUX`, `NUL`, `CONIN$`, `CONOUT$`, `COM0` à `COM9`, `LPT0` à `LPT9`, `COM¹²³`, `LPT¹²³`. Un nom refusé n'est **jamais corrigé** : l'élément est ignoré et compté (« noms refusés » dans le bilan du transfert). Un listage écarte en plus les entrées qui ne désignent pas un élément unique (`.`, `..`, `/`, NUL).
    - **Écriture locale** : chaque fichier est écrit dans un fichier temporaire **du dossier de destination**, puis renommé ; sans écrasement demandé, le renommage refuse d'écraser (`persist_noclobber`). Le renommage remplace l'entrée elle-même : un lien symbolique planté dans la destination n'est jamais suivi. Chaque dossier créé est canonicalisé et doit rester dans la racine choisie. Un transfert annulé ne laisse pas de fichier partiel local ; côté serveur, seul un fichier **créé** par l'envoi est supprimé (un fichier écrasé n'est pas restaurable).
    - **Liens symboliques** : les liens distants ne sont pas suivis en récursif (attributs `lstat`) ; un lien **sélectionné explicitement** est résolu. Les liens locaux ne sont pas suivis à l'envoi. La suppression distante récursive supprime les liens, jamais leur cible.
    - **Bornes face à un serveur abusif** : listage de 10 000 entrées affichées, 20 000 requêtes READDIR et 120 s au plus ; paquets SFTP de 256 Kio au plus (vérifiés avant allocation) ; 30 s par requête ; profondeur 64 et 100 000 éléments par opération récursive ; résolution des cibles de liens d'un listage limitée à 256 liens et 10 s au total. Les listages passent par `RawSftpSession`, car `SftpSession::read_dir` de `russh-sftp` n'est pas borné.
    - **Conflits** : l'IPC n'accepte aucune politique de conflit (toujours « demander ») ; sans réponse en 10 min, l'élément et les conflits suivants du transfert sont ignorés, jamais écrasés.
    - **Noms affichés** : caractères de contrôle et invisibles remplacés par `�` ; un nom modifié ou refusable est signalé dans la liste (« nom inhabituel »).
    - **Fichiers téléchargés** : 0600 sous Linux, sans reprendre les droits distants ; sous Windows, Mark-of-the-Web posée au mieux (`Zone.Identifier`, `ZoneId=3`) pour que SmartScreen et le mode protégé d'Office s'appliquent.
    - **Édition (SFTP-05)** : copie dans `<app_local_data>/edits` (0700 sous Unix), puis dans un sous-dossier aléatoire `younji-edit-*`, fichier 0600, 16 Mio au plus. Le nom distant passe par `check_local_name`. Ouverture dans un éditeur imposé, jamais l'application associée (ADR-034). Avant chaque renvoi, la taille et la date distantes sont comparées : si le fichier a changé, le renvoi est suspendu et un conflit est signalé ; seul un renvoi forcé écrase. La copie est supprimée à la fermeture de l'édition, à la fin de la session et au verrouillage ; au démarrage, les copies abandonnées depuis plus de 24 h sont supprimées (les plus récentes peuvent appartenir à une autre instance).
- **Suivi du dossier du shell (OSC 7, étape 4)** : le chemin annoncé par le serveur est une donnée non fiable. Il est décodé strictement (`file://hôte/chemin`, encodage en pourcentage, 4 096 caractères au plus) et refusé s'il contient des caractères de contrôle, invisibles ou bidirectionnels ; le nom d'hôte est ignoré. Il ne sert qu'à lister ce même serveur, et le cœur le revalide. L'intégration au prompt (bash, zsh) est un **texte constant**, inséré seulement sur clic explicite, comme un collage (encadré si le programme distant a activé le mode « bracketed paste »), **sans Entrée** : l'utilisateur le relit et le valide lui-même. Il commence par une espace pour rester hors de l'historique.
- **Messages du serveur** (bannière, questions keyboard-interactive) : affichés comme du texte, jamais interprétés comme du HTML. Les bannières sont nettoyées de toute séquence de contrôle (échappements ANSI, OSC) avant affichage, plafonnées à 8 Kio chacune et 64 Kio par session, et comptées dans le contrôle de flux : un serveur ne peut ni piloter le terminal ni inonder l'interface avant l'authentification.

### 4.3 RDP
- **v1 (client système)** : le mot de passe n'est **jamais** passé en argument de ligne de commande, car il serait visible dans la liste des processus.
  - Windows : identifiant écrit via l'API `CredWriteW` (cible `TERMSRV/<hôte>`), jamais via `cmdkey /pass:`. Il est supprimé à la fin de la session `mstsc` ou après un court délai. Le fichier `.rdp` temporaire, créé avec un nom aléatoire, est supprimé après usage.
  - Linux : `xfreerdp` reçoit le mot de passe par l'entrée standard (`/from-stdin`).
- **v2 (IronRDP)** : le certificat du serveur est vérifié en TOFU, avec la même logique que les clés d'hôte SSH. NLA (CredSSP) est exigé par défaut.

### 4.4 Tunnels
> Sans objet pour l'instant : la fonction tunnels est retirée (ADR-038). Ces règles restent en vigueur et s'appliqueraient telles quelles si elle revenait.

Écoute sur `127.0.0.1` par défaut. Écouter sur `0.0.0.0` demande une confirmation explicite et affiche un indicateur permanent dans la liste des tunnels.

## 5. Durcissement de l'application Tauri
- La WebView est **non fiable**. Toute entrée IPC est validée côté Rust : types, longueurs, ports (1–65535), chemins canonicalisés, identifiants existants.
- **Les secrets ne transitent qu'une fois**, de l'interface vers le cœur au moment de la saisie. Ensuite, l'interface manipule des identifiants (`identity_id`). Aucune commande ne renvoie un secret.
- CSP stricte, aucun contenu distant, `withGlobalTauri: false`, capabilities minimales par fenêtre, pas de plugin `shell` exposé à l'interface. Seule exception aux styles en ligne : `style-src-elem 'self' 'unsafe-inline'`, pour les balises `<style>` que xterm.js injecte (ADR-018). `style-src 'self'` reste strict en production : les attributs `style` restent interdits. Risque jugé faible, car `img-src`, `font-src` et `connect-src` n'autorisent aucune origine distante, donc une feuille de style injectée ne peut rien exfiltrer. Un test vérifie que `'unsafe-inline'` n'apparaît que dans les directives de style. Détails dans `.claude/rules/tauri-config.md`.
- **`freezePrototype`** : Tauri gèle `Object.prototype` avant tout script, contre la pollution de prototype par une dépendance compromise. Toute dépendance de l'interface doit le supporter : un test charge l'application et un terminal avec le prototype gelé (`src/frozen-prototype.test.tsx`). C'est ce qui a conduit à garder xterm.js 5.5 (ADR-025).
- **Modèle d'isolation Tauri** (iframe sandboxée qui intercepte l'IPC) : **activé** depuis l'étape 0 (ADR-015), avec une liste blanche de commandes (`isolation/index.js`). C'est une défense en profondeur **« au mieux »**, pas une barrière : un test sur build réel (17/11/2026) a montré qu'un script de la fenêtre principale qui intercepte `fetch` récupère la clé d'invocation et appelle une commande directement, sans passer par l'iframe (le nom de commande est dans l'URL, non authentifié). Les vraies barrières restent les **capabilities** et la **validation côté Rust** de chaque entrée. On n'accorde jamais une permission en comptant sur le filtrage de l'isolation, et on ne lui confie aucune validation de charge utile. Seule commande interne de Tauri admise par l'isolation : `plugin:__TAURI_CHANNEL__|fetch`, nécessaire pour récupérer les messages de `Channel` de plus de 1 Kio (sortie du terminal). Tauri l'exempte d'ACL ; elle ne renvoie qu'un message déjà destiné à la fenêtre, une seule fois, désigné par un identifiant aléatoire (ADR-024). Un test vérifie qu'aucune autre commande interne n'est admise.
- **Inspecteur web** : disponible uniquement en compilation de développement (`npm run tauri dev`, clic droit → Inspecter). La version publiée ne l'embarque pas : la fonctionnalité `devtools` de Tauri n'est pas activée et aucune fenêtre ne l'ouvre par code. Un test (`tests/security/tauri-config.test.ts`) échoue si cela change. Raison : la console donnerait un accès direct à l'IPC à toute personne devant le poste.
- **Navigation** : la fenêtre principale ne peut naviguer que vers l'origine de l'application (et le serveur Vite en développement) ; l'ouverture de nouvelles fenêtres est refusée (`src-tauri/src/navigation.rs`). La CSP ne couvre pas la navigation de premier niveau.
- **Rechargement de l'interface** : au début de chaque chargement de page, le cœur ferme toutes les sessions SSH. Les `Channel` de l'ancienne page sont perdus : les sessions n'auraient plus personne pour les piloter, et leurs secrets resteraient en mémoire. Hors du terminal, F5 et Ctrl+R sont bloqués pour éviter une fermeture accidentelle ; dans le terminal, xterm.js les transmet au shell.
- **Sélection de fichiers** : la boîte de dialogue est ouverte par le cœur (`tauri-plugin-dialog` utilisé depuis Rust, aucune permission du plugin accordée à la WebView). Le chemin choisi reste dans le cœur ; l'interface ne reçoit qu'un identifiant opaque et le nom du fichier (ADR-020).
  - **Dossiers locaux du SFTP (étape 4, ADR-034)** : même principe. Un dossier choisi devient une « racine » désignée par identifiant ; aucun chemin local absolu n'est accepté de l'IPC, et les chemins relatifs sont canonicalisés et confinés à la racine. `RootPolicy` refuse la racine d'un disque, le dossier personnel entier et ses ancêtres, `~/.ssh` et son contenu, et les dossiers de données de l'application (coffre, journaux, copies d'édition). Le panneau local ne propose ni suppression ni renommage. Les racines sont oubliées au verrouillage et au rechargement. **Risque résiduel** : une interface compromise peut lire, créer et écraser des fichiers dans une racine autorisée (en répondant « écraser » à un conflit) tant que le coffre est déverrouillé ; une confirmation native de l'écrasement local par le cœur est envisagée.
- **Glisser-déposer** (étape 4) : le gestionnaire natif de Tauri est désactivé (`disable_drag_drop_handler`), pour ne pas exposer à la WebView les chemins des fichiers déposés depuis le système. Seul le glisser-déposer interne entre les panneaux SFTP est pris en charge ; un dépôt venant du système est ignoré.
- **Journaux** : `YOUNJI_LOG` ne règle que le niveau du code de Younji ; les dépendances restent plafonnées à `warn`, pour qu'un niveau `trace` ne fasse jamais journaliser des paquets ou des arguments IPC.
- **Commandes applicatives soumises aux capabilities** : chaque commande est déclarée dans `src-tauri/build.rs` et doit être accordée explicitement (`allow-<commande>`) dans une capability. Un test (`tests/security/tauri-config.test.ts`) vérifie la cohérence entre `build.rs`, la liste blanche de l'isolation et les capabilities, ainsi que les invariants de la CSP.

## 6. Fuites par effet de bord
- **Journaux** : jamais de secret, jamais le contenu du terminal ni des fichiers transférés. L'hôte, le port et l'utilisateur sont tolérés au niveau `debug`. Les types qui contiennent des secrets ont un `Debug` masqué.
  - **SFTP (étape 4)** : aucun nom de fichier, chemin ni contenu dans les journaux ; seulement des compteurs (bilan d'un transfert, copies d'édition supprimées), des identifiants opaques et des codes d'erreur. Le texte d'état renvoyé par le serveur SFTP n'est ni journalisé ni recopié dans les erreurs : il est traduit en code stable. Les erreurs et les événements de transfert ne renvoient à l'interface aucun chemin local.
- **Erreurs** : codes stables (`ssh.auth_failed`), sans écho de l'entrée utilisateur ni du secret.
- **Processus externes** : aucun secret dans les arguments ni dans les variables d'environnement visibles.
- **Variables d'environnement envoyées au serveur SSH** (étape 5) : uniquement `LANG=C.UTF-8` et `LC_CTYPE=C.UTF-8`, valeurs constantes, pour que le shell distant accepte les lettres accentuées tapées au clavier. Rien du poste n'est transmis (ni langue, ni nom d'utilisateur local) ; le serveur peut la refuser (`AcceptEnv`) ou la redéfinir (fichiers de profil du shell).
- **Fichiers temporaires** : noms aléatoires, permissions restrictives, suppression garantie, y compris en cas d'erreur (`Drop`).
- **Crash** : pas de rapport de plantage envoyé (aucune télémétrie).
- **Diffusion multi-sessions** : indicateur visuel impossible à manquer et confirmation à l'activation.
  - **Mise en œuvre (étape 5, ADR-036)** : diffusion gérée par l'interface au-dessus de `ssh_write`, sans nouvelle commande IPC. Activation seulement après un dialogue qui liste chaque session par nom et adresse ; seule la session active est cochée d'office, 2 cibles au moins. Jamais persistée ; arrêt au verrouillage et sous 2 cibles ; une cible déconnectée est retirée définitivement (une reconnexion ne la réintègre pas). Bandeau rouge global avec arrêt en un clic, bordure rouge et en-tête « DIFFUSION » sur chaque cible, pastille sur les onglets. Un collage diffusé est **toujours** confirmé (le dialogue liste les serveurs) et encadré selon le mode « bracketed paste » de chaque cible. **Seule la saisie de l'utilisateur est diffusée** : les réponses automatiques du terminal (position du curseur, identification, focus, souris, OSC, DCS) restent dans leur session, pour qu'un serveur ne puisse pas écrire dans les autres. Limites : attribution par une fenêtre de 100 ms après une frappe (à surveiller avec IME et AltGr) ; Maj+F3 n'est pas diffusé.
- **Snippets (étape 5, ADR-037)** : stockés dans le coffre, donc chiffrés au repos, mais **ce ne sont pas des secrets** (affichés, envoyés en clair au terminal). Contenu validé par le cœur à l'enregistrement **et au chargement** : 16 Kio au plus, aucun caractère de contrôle hors `\n` et `\t`, aucun caractère invisible (bidirectionnel, largeur nulle, BOM), 32 variables au plus. Valeurs des variables sur une ligne, sans caractère de contrôle ni invisible ; aucun échappement shell automatique, l'aperçu montre le texte exact. « Insérer » (sans Entrée) par défaut ; l'envoi vise les seules sessions cochées et ignore la diffusion. Ni le nom, ni le contenu, ni les valeurs ne sont journalisés.
- **Identités et clés du coffre (étape 2, ADR-030)** : une clé importée est déchiffrée une fois avec sa passphrase, puis stockée **sans** passphrase dans le coffre, qui la protège ; la passphrase n'est pas conservée. Le cœur ne renvoie jamais à l'interface ni le mot de passe d'une identité (seulement `hasPassword`) ni une clé privée (seulement la clé publique, sans commentaire, et l'empreinte). Une connexion depuis le carnet désigne l'hôte par son identifiant : aucun secret ne transite par l'interface, reconnexion comprise.
- **Clés générées (étape 3, KEY-01)** : Ed25519 (défaut), ECDSA P-256/P-384/P-521, RSA 4096 ; aléa du système uniquement (`getrandom::SysRng`, équivalent d'`OsRng`). La clé naît dans le cœur et va directement dans le coffre, sans passphrase (même traitement qu'une clé importée, ADR-030) ; aucun export de la clé privée. L'export de la **clé publique** écrit un fichier choisi dans la boîte de dialogue du système ouverte par le cœur (ADR-020), de façon atomique ; l'extension `.pub` est imposée (un nom tapé sans extension ne peut pas écraser la clé privée voisine), et un fichier que la boîte de dialogue n'a pas confirmé n'est jamais écrasé.
- **Limites mémoire connues (étape 3)** : russh reçoit les réponses keyboard-interactive (codes, mot de passe rempli automatiquement) sous forme de `String` ordinaires, non effacées par Younji ; le corps JSON de `ssh_auth_answer` et de `key_deploy` (mot de passe éventuel) passe par les tampons de la WebView et de Tauri. Même traitement et même limite que ci-dessous.
- **Limites mémoire connues (étape 2)** : comme russh, la crate `zxcvbn` copie le mot de passe maître dans des chaînes internes qui ne sont pas effacées ; les corps JSON des commandes qui transportent un secret (`vault_create`, `vault_unlock`, `vault_change_password`, `identity_save`, `key_import`) passent par des tampons de la WebView et de Tauri qu'on ne peut pas effacer. Même traitement et même limite que ci-dessous.
- **Limites mémoire connues (étape 1)** : russh reçoit le mot de passe sous forme de `String` ordinaire pendant l'authentification, et cette copie n'est pas effacée par Younji. Le corps JSON d'un appel IPC qui transporte un secret (`ssh_connect`) passe par les tampons de la WebView et de Tauri, qu'on ne peut pas effacer. Le cœur place le secret dans un `SecretString` dès la désérialisation, détruit les identifiants dès la fin de l'authentification, et l'interface vide le champ dès l'envoi. Ces copies résiduelles relèvent de la limite déjà décrite au §3.5 et du hors-modèle du §2 (lecture de la mémoire par un malware local).

## 7. Mises à jour et signature
- **Mises à jour** (étape 13) : `tauri-plugin-updater` avec une signature ed25519 (`tauri signer generate`). La clé publique est dans `tauri.conf.json`. La clé privée et sa passphrase vivent **uniquement** dans les secrets GitHub (`TAURI_SIGNING_PRIVATE_KEY`, `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`), avec une copie de secours hors ligne chez le porteur. **Jamais dans le dépôt**, et Claude Code n'y a pas accès.
- **Signature du code Windows** : aucune pour l'instant (avertissement SmartScreen accepté). Le dépôt étant public depuis l'étape 0 (ADR-016), la demande auprès de la SignPath Foundation (gratuite pour les projets open source sous licence approuvée par l'OSI) peut être faite dès qu'une première version est publiée.

## 8. Chaîne d'approvisionnement
- `Cargo.lock` et `package-lock.json` sont commités. La CI utilise `npm ci`.
- `cargo-deny` : avis RustSec, licences compatibles GPL-3.0, sources limitées à crates.io, doublons signalés.
- `npm audit --audit-level=high` en CI, Dependabot hebdomadaire (cargo, npm, actions).
  - **Exception en cours (17/11/2026, décision du porteur)** : l'avis [GHSA-fc5q-39xc-vjpf](https://github.com/advisories/GHSA-fc5q-39xc-vjpf) (ReDoS dans `picomatch` ≤ 4.0.7) n'a aucune version corrigée. `picomatch` n'est utilisé que par l'outillage de développement (Vite, Vitest, ESLint), avec nos propres motifs de fichiers, et n'est pas embarqué dans l'application. En attendant un correctif : l'audit des dépendances **embarquées** (`npm audit --omit=dev --audit-level=high`) reste bloquant, et l'audit complet est affiché en CI sans bloquer. **À retirer dès qu'une version corrigée de `picomatch` est publiée** : rétablir l'audit complet bloquant dans `ci.yml` et dans `npm run audit`.
- Actions GitHub épinglées par SHA, `permissions` minimales, gitleaks à chaque push.
- Chaque nouvelle dépendance est justifiée : utilité, maintenance active, licence, surface d'attaque.
